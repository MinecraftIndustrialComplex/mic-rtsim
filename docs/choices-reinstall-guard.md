# Choices: the reinstall guard (UR-1) and the first detection's long tick (R2-11)

Branch `feat/reinstall-guard`, 2026-10-23. Reversible choices made without asking, each with what and
why. Ben's decisions are at the end ("For Ben"); none blocks the work.

Verified against Minecraft 1.21.1 / NeoForge 21.1.249 sources (the neoform
`sourcesAndCompiledWithNeoForge` jar).

## Part 1: the reinstall guard

What it must do (UR-1): see at a start that the world ran without rtsim, then reset the whole sim,
loudly, recover what it can from the world without a player's help, and never replay a reconcile.
Round 2 of the deploy rehearsal (docs/deploy-rehearsal-omegasrv.md 10.6) showed what happens without
it: rtsim restores its pages as they were, and every district dissolves as its chunks load, because the
gap's saves dropped their `mic_rtsim:industry_seeds` attachments.

| Id | Choice | Why |
|---|---|---|
| RG1 | **The gap is read from `level.dat`'s mod list, at the start's read of it.** NeoForge writes the loaded mods into `level.dat` (root `fml.LoadingModList`, `[{ModId, ModVersion}]`) on every write of it, and reads it back once per start through `CommonHooks.readAdditionalLevelSaveData` (dedicated: `Main`, before its boot write of `level.dat`; integrated: `WorldOpenFlows`, when a world is opened; never the world list, never `GameTestServer`). A mixin at that method's `HEAD` (`CommonHooksLevelDatMixin`, PATCHES.md row 47) hands the root tag to `ReinstallGuard.levelDatRead`, which never throws. Cost: one scan of the mod list per start. | The read is the one moment that sees what the previous writer was: the start rewrites `level.dat` with rtsim in the list. A dedicated server without rtsim writes `level.dat` at its boot, before any chunk loads, so any gap that saved a chunk on a dedicated server is in the list. NeoForge's own `ModMismatchEvent` reports missing and changed mods, never added ones, so it cannot say this. Rejected: comparing `level.dat`'s game time with the journal's or the pages' (a crash and the 10 s SavedData cooldown give differences of seconds, so it needs a threshold and has false positives); a per-chunk "rtsim saw this chunk" stamp (seen only as chunks load: late and partial). |
| RG2 | **What a read concludes** (`ReinstallRules.classify` and `decide`): a list that holds `mic_rtsim` is no gap; a list without it is a gap when the world holds rtsim's state (a non-empty `world/rtsim/`, or any `world/data/mic_rtsim*.dat`), else a first install; a `level.dat` with no `fml` tag (a vanilla server or another loader wrote it last) is a gap on the same condition; an `fml` tag without a readable list decides nothing and logs a warning. Versions are not compared. | The edge cases, each a unit test in `ReinstallRulesTest`: a **normal restart** and a **crash** (the crash leaves the last save's `level.dat`, which a server with rtsim wrote) are no gap; a **crash between two writes** (`level.dat` and the SavedData, or the chunks) is no gap, both writes came from the same server; a **deliberate sim reset** (8.6: `world/rtsim/` deleted, rtsim installed) is no gap, its new pages take the re-announce path (`observationsLost`) and a new engine life (RG13) on their own; the **first install** has no state and no reset; a **format change** (another `ModVersion` of `mic_rtsim`) is no gap, SRV2's sim reset handles formats; a **backup restore** of a world saved with rtsim is no gap, one saved during a gap is a gap (its chunks ran without rtsim), and a restore without `world/rtsim/` is the sim reset's case. |
| RG3 | **A gap is written down at once: `world/mic_rtsim-reinstall.txt`.** The read writes the marker (reason, time, game time) to a temporary file, syncs it, renames it and syncs the directory, before the start rewrites `level.dat` with rtsim in its list. Every start that finds the marker resets (`ReinstallRules.resets`: marker or a gap read). The marker goes after the reset's first overworld save: `ReinstallGuard.onOverworldSave` (from `LevelEvent.Save`, after the save data queued their writes) queues the deletion on NeoForge's save-data chain (`IOUtilities.withIOWorker`), so behind the industry data that holds the re-adoption list (RG7). | Without the marker, a crash after the start rewrote `level.dat` and before the reset reached disk would leave a world whose `level.dat` says "rtsim ran" and whose pages are the stale ones: the gap would be forgotten. A second reset (a crash before the first save) is harmless: the engine is new anyway, and the re-adoption list is planned again from the same districts. |
| RG4 | **The reset moves `world/rtsim/` to `world/rtsim-reinstall-<UTC time>/`, before the engine opens.** It is never read again; the admin deletes it. If the move fails, there is no session (`RtsimSession.startFailure`, shown by `rtsim perf`), never a partial reset. | The pages are the sim's whole state, so the reset is "the engine starts empty", the same as runbook 8.6's sim reset (SRV2). Moving keeps them for a look or an undo (RG9) at the cost of their size on disk. |
| RG5 | **The journal and the world's `data/mic_rtsim*.dat` are kept.** The new engine gets the journal's unacknowledged observations as after any start; with new pages, `BoundarySession.observationsLost` is true and every module announces what it knows again (districts, villages, bases, the industry's declarations). | Exactly runbook 8.6's state, which the re-announce path was built for and round 2 measured (10.6). The world's saved data is how the bridge knows what to announce. |
| RG6 | **No reconcile replays.** What the old engine owed (its pending reconciles, its outbox) lives in its pages, which are moved aside, so nothing is sent again. Java holds reconciles in memory only. A result a chunk still carries from the old engine is dropped at the chunk's load with its epoch (RG13), not journaled again, and so are the pending records chunks and entities carry (RG14). The journal's applied op ids still answer DUPLICATE_OP to an op id seen before. | The UR-1 row's worry ("a reconcile applied but not yet acknowledged could replay") was about restoring the old pages after the gap stripped the chunks' `mic_rtsim:reconcile` markers; the reset never restores them. |
| RG7 | **Districts whose seeds the gap stripped are adopted again, chunk by chunk, as the chunks load.** At the reset, `Districts.planReadopt` lists every member chunk with a seed count above 0, per dimension, in the industry data (`readopt`, saved). When a listed chunk loads (or at the session's start, for chunks already loaded) it leaves the list; if its seed attachment is gone, its machines are adopted as `rtsim district adopt` with radius 0 would (every block entity that seeds or may become a seed), before any detection looks at it; if the attachment is there, the chunk did not load during the gap and is left alone. `rtsim perf` shows the progress ("re-adoption after the reinstall reset: N chunks adopted again (M machines), K kept their seeds, L not loaded yet"). | Without it, every district dissolves as its chunks load (round 2). Only stripped chunks are touched, so a chunk that never loaded during the gap keeps its exact seeds. Re-adopting every machine of a stripped chunk can add a machine that was not a seed before (one a player never placed in a chunk adopted by area); that only makes the district what an adopt would. |
| RG8 | **What the reset loses, and what an admin still does.** Lost: the sim's economy and memory (SRV2: stocks owed to unloaded chunks, learned recipes, the engine's knowledge); players' block marks (`player_blocks`) in chunks that loaded during the gap; machines a player built during the gap in a chunk that was not a district member (`rtsim district adopt` them). The admin deletes `world/rtsim-reinstall-*` when satisfied. | The loud lines say it: the read logs ERROR `[mic_rtsim] REINSTALL: ...` with the marker's path, the start logs ERROR `[mic_rtsim] REINSTALL RESET (UR-1): ...` with what moved where and what is lost, `[industry] reinstall reset: N chunks of M districts are adopted again as they load` follows, and `rtsim perf` carries a `reinstall guard: SIM RESET at this start (UR-1): ...` line for the whole session. |
| RG9 | **No switch to turn the guard off.** To undo a reset: stop, move `world/rtsim-reinstall-<time>/` back to `world/rtsim/`, delete `world/mic_rtsim-reinstall.txt` if it is still there, start. A boot without rtsim that loaded no district chunk (the jars forgotten, the server stopped at once) still resets: the guard cannot tell which chunks a gap saved, and the undo is the way back for an admin who knows the gap was harmless. | The guard acts only on a list without `mic_rtsim` in a world that holds rtsim's state, which is never a normal start; restoring the old pages is the very case UR-1 forbids, so it is an admin's deliberate step, not a setting. |
| RG10 | **Not covered.** (1) A gap of a plugin alone (the core ran, `mic_rtsim_create` did not): the core's state is right, the plugin's attachments in the gap's chunks are gone; the module switch (U10) does not see it either. (2) A single-player world opened without rtsim that crashed before its first `level.dat` write but after a chunk unload saved a chunk: the integrated server has no boot write. (3) A crash after the marker's deletion and before the chunks with re-adopted seeds reach disk: the chunk writes go through another IO worker than the save data, so the industry data can say "adopted" for a chunk whose seeds are not on disk; that district loses the chunk at its next detection. The window is the time between the save data's write and the chunks' write of one save. | (1) and (2) are outside the dedicated server's deploy; (3) needs a crash in a window of seconds once per reinstall. |
| RG11 | **Test hooks.** `RtsimSession.restartGlobalForTest` (stopping, a full save, stop, start, in the running GameTest server), `ReinstallGuard.pendingCapture`, `forgetCaptureForTest` and `markerCleared`. `ReinstallGameTests` calls NeoForge's own hook with a `level.dat` whose list lacks `mic_rtsim`, strips every `mic_rtsim*` attachment from the chunks that "load during the gap", moves the clock on by 6,000 ticks and restarts the session; its timeout is 20,000 ticks because a GameTest's tick count is the level's game time minus its start, which the clock move counts. | The GameTest server never reads `level.dat` (RG1), so the test drives the real hook rather than a copy of its logic. |

## Part 2: what chunks and entities hold across a sim reset

| Id | Choice | Why |
|---|---|---|
| RG13 | **An applied reconcile epoch carries the engine life that issued it.** Found while checking RG6: after any sim reset (runbook 8.6 or RG4) the engine numbers each district's epochs from 1 again, while the chunks keep the epochs the old engine applied in their `mic_rtsim:reconcile` attachment. Java answered the new engine's reconciles as DUPLICATE_OP (`Reconciler.apply`: the chunk holds that epoch or a later one), and the engine, told at the chunk's load that a later epoch was applied, took its own pending ones as applied as asked (engine.rs, `ChunkLoaded`): the district's reconciled goods were lost, and its books disagreed with the world, until its new epochs passed the old ones. Now the page directory carries an engine life, `world/rtsim/bridge-life.txt` (written, synced and renamed before the session runs). A directory that has one keeps it at every start. A directory without one gets a random life when its engine starts over (`ReinstallRules.startsOver`: its pages include no observation, `pagesObsSeq` 0, and the journal no longer holds what earlier pages included, `observationsLost`), else 0: a first install loses nothing, and pages from before the file carry entries without a life. An engine that crashed before its first page save finds the file its first session wrote and keeps the life: it replays the same journal and numbers its epochs as before. A file that does not parse fails the start (no session, `rtsim perf` says why), never a guess. Each epoch entry stores its life (`life`, a `long`, 0 when absent). At a district chunk's load, entries of another life are dropped, their unacknowledged results with them (`staleEpochs` in `rtsim district perf`), and an entry of another life reads as epoch 0. The engine and the wire are unchanged. Tests: `theEngineLifeChangesExactlyWhenThePagesStartOver` and `theEngineStartsOverOnlyWhenItsHistoryIsGone` (ReinstallRulesTest) and the epoch steps of `aReinstallResetsTheSimAndAdoptsTheStrippedDistrictsAgain` (C holds epoch 40 of the old life; after the reset it is dropped and the new engine's epoch 1 applies, no duplicate). | The life file sits in the page directory, so it goes wherever the pages go: 8.6 deletes it, RG4 moves it, a backup restores it with its pages. A counter in the industry data was rejected: a crash after a chunk saved an entry of the new life and before the industry data saved the counter would make that entry look stale to a restart on pages that had saved, and the engine would send its pending epochs again: a replay. A life other than 0 is only ever drawn after the journal was first trimmed, so every later new directory sees `observationsLost` and draws again: a directory never inherits a stale life. Not covered: (1) pages restored from an older backup than the chunks (same life, older epochs): the engine's epochs are behind the chunks' until they catch up; that was so before, and is the journal's `observationsLost` case, not a reset. (2) The industry engine starting afresh inside kept pages because its pages do not decode (W23, another build's format): the life stays, so chunks' epochs block its new ones, and Java does not announce the districts again either; the runbook's answer to a format change is the sim reset (8.6), which does start over. (3) `world/rtsim/` deleted together with the world's journal (`data/mic_rtsim_journal.dat`), off the runbook: nothing is lost by the journal's count, so a world whose life was 0 keeps 0. |
| RG14 | **Pending records carry the engine life too, and a holder of another life drops them unjournaled.** `mic_rtsim:pending` (PendingRecords, docs/boundary.md §3.1) is now `{life, records}`: every add stamps `RtsimSession.engineLife` (a holder carries one life; an add in a new life replaces records of the old one), and `reassert` at the holder's load drops records of another life without journaling them (`stalePending`, shown in `rtsim perf`'s journal line next to the records journaled again). `chunkCarriesOp` counts only this life's records, so an op id of the old engine never blocks one of the new. A plain list from before the life reads as life 0. Tests: the D chunk of `aReinstallResetsTheSimAndAdoptsTheStrippedDistrictsAgain` (a COMMAND_RESULT of the old engine, unacknowledged when D unloads, kept through the gap; at D's load after the reset it is no op of the new engine and is dropped, nothing journaled) and `pendingRecordsKeepTheirEngineLife` (NBT round trip, the old plain list). | Raised by SEC-1: a chunk that unloads before the engine acknowledges its records keeps them, and journals them again at its next load, after `WORLD_SAVED` let the engine forget the op, so a record with an effect of its own needs dedup beyond the op id (SEC-1 S4b's per-frogport WriteMark). Across a sim reset no engine-side mark can help: the new engine's pages are new, and it took what the world holds from the world (re-announce, re-adoption), so a record of the old engine journaled into it could only apply a second time what the world already shows. Within one life nothing changes: a crash, a restart and a restored backup with its pages keep the life and journal the records again as before. A chunk that loaded during the gap lost the attachment with the others (NeoForge drops unknown attachment types), the same outcome. Records that a module adds (SEC-1's) get this for free as long as they go through `PendingRecords.plus` with the session's life. Not covered: the old engine's unacknowledged journal tail (at most one save interval, RG5) still reaches the new engine, as in runbook 8.6; the engine drops most of it (unknown op ids, members and districts, which are announced again after it), and a module whose records have an effect of their own must keep that in mind until the bridge skips the tail of an earlier life. |

## Part 3: the first detection's long tick (R2-11)

What R2-11 saw (docs/deploy-rehearsal-omegasrv.md 10.6): where districts exist at a start, the session's
first detection spent 0.68 to 2.2 s in one tick. Reproduced on two copies of r-reset-reload's world without
its `world/rtsim/` (p2-a with no time limit, p2-b with RG12's), each base forceloaded 20 s after the start, as
10.6's runs do, and started twice:

| Run | Longest detection tick | Block entities in it | Longest look at one chunk | Chunks loaded meanwhile |
|---|---|---|---|---|
| p2-a, no time limit | 2,205 ms | 276 | 2,177 ms | 972 (first by `create:depot`) |
| p2-b, time limit 5 ms | 1,136 ms | 30 | 1,136 ms | 680 (first by `create:belt`) |
| p2-b again, same world | 588 ms | 71 | 586 ms | 534 |
| p2-a again, same world | 11 ms | 274 | 9 ms | 0 |
| p3b, the reinstall rerun's restart | 10 ms | 234 | 9 ms | 0 |

The time was not cold code, as 10.6 first read it, but chunk loads inside one look at one chunk: the
detection asks only loaded chunks, and still hundreds of chunks loaded while it looked.

| Id | Choice | Why |
|---|---|---|
| RG12 | **A detection's tick also stops at a time limit: `rescanSliceMicros` (industry config), default 5,000 us, 0 for none.** `Districts.Rescan.step` looks at chunks until the block entity budget (`rescanBlockEntitiesPerTick`, 256) or the time limit, whichever comes first, and always at least one chunk a tick. The cut falls only between chunks, and nothing commits until every chunk is looked at, so a detection spread over more ticks finds the same districts. Counters: `rtsim district perf` gives the longest tick (its block entities, the longest look at one chunk, the classes and chunks loaded meanwhile) and `rtsim perf`'s industry block "last detection: longest chunk N us, C classes loaded, L chunk loads (first by <block entity type>)". The first chunk load inside a detection step logs its stack once a session, as a warning. GameTests run at the default, except `anAdoptThatFitsTheBudgetIsDetectedInTheCall`, which is about the count budget and sets 0. Test: `aTickStopsAtTheTimeLimitAndDetectsTheSame` (RescanBudgetGameTests: at 1 us, one chunk a tick, four ticks at least for four chunks, the same chunks and seeds as a one-call detection, no chunk loaded). | The budget counts block entities, so a tick whose block entities cost more than usual (cold classes, a slow plugin) had no bound. 5 ms is a tenth of a tick: a detection of a large base (about 800 machines) still finishes within seconds. It cannot bound one look, which is why RG15 was needed: p2-b's 30-block-entity tick still took 1.1 s. |
| RG15 | **Fan links read only FULL chunks (the cause).** The stack RG12's watch caught: `FanLinks.fromHost` asked `Level.isLoaded` and then `getBlockState` along a host's rays. `isLoaded` asks only the chunk's ticket level, so a chunk that is due but still loading (the forceload's chunks, at a start) passes it; `getBlockState` then waits for that chunk in `managedBlock` (C2ME's `instrumentAwaitChunk` on this pack), which runs the server thread's task queue, and every other chunk load due completes inside the look. Now every read of `FanLinks` goes through `Loaded` (`getChunkNow`: a chunk that is not FULL reads as not loaded), and a fan's flow limit is cut short of the first chunk that is not FULL before Create's `AirCurrent.getFlowLimit` reads it, as the glass compile's `FanCurrent` already did. For loaded chunks the links are the same; a chunk still loading is treated as unloaded, as the rest of the detection treats it, and its load marks it for the next detection, which links it. Test: `aLinkNeverWaitsForAChunkStillLoading` (GlassFanLinkGameTests: a fan's chunk held at level 34, given a FULL ticket and the distance manager's updates in the same tick; the depot's links must not name the fan and the chunk must still not be FULL after the look; once it loads, the fan is linked). | The core's own reads (`describe`, `canonicalInventory`, the walk) already went through `getChunkNow`; the plugin hook was the gap. A wait is never bounded by a time limit, so the read itself had to change. |
| RG16 | **Not changed: other `Level.isLoaded` reads outside detection.** The same test passes chunks still loading in `TrainWatch`, `WritePackages` and `MailWatch` (create), `PowerLinks` (powergrid, tick sampling), `Nests` and `Lairs` (iceandfire), `RadarPlugin.facts` (radar), `ResidentSpawner` (growth), `ConflictBridge` and `HerdBridge` (`hasChunk`), and `FarHide` (dh, `hasChunk`). None is in a detection step. | Each can make its own tick wait for a load the same way; a finding for their owners (`Loaded`, or `getChunkNow`, is the fix), not this branch's. |

## For Ben

None of these blocks the work; each was taken as recommended and can be changed.

1. **RG9: no switch to turn the guard off.** Any boot without rtsim resets the sim at the next start,
   even one that stopped at once and stripped nothing; the sim's economy and memory go with it (SRV2).
   The alternative is a config key that skips the reset (an admin who knows the gap was harmless).
   Recommended: no switch; undoing is three file moves (RG9).
2. **RG7: a stripped chunk gets every machine adopted, not only its old seeds.** The alternative keeps
   the seed positions in the industry data (one `long` per seed, saved per district) so exactly the old
   seeds come back. Recommended: as built; an adopt is what an admin would have run.
