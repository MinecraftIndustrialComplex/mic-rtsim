# Choices: reconcile ahead of arrival (Java side) and repair schematics (I1)

Branch `feat/reconcile-ahead-repair`, 2026-10-20. Reversible choices made without asking, each with
what and why. Ben's decisions are at the end ("For Ben"); none blocks the work.

Verified against Minecraft 1.21.1 / NeoForge 21.1.249 sources (the neoform `sourcesAndCompiledWithNeoForge`
jar) and the Create 6.0.10 jar (decompiled).

## Part 1: reconcile ahead of arrival

| Id | Choice | Why |
|---|---|---|
| R1 | **A held reconcile lands at its chunk's load, before IND_CHUNK_LOADED.** At the drain of a loaded chunk, `Reconciler.chunkLoaded` journals again any unacknowledged result the chunk carries, applies every command held for the chunk in epoch order, then journals IND_CHUNK_LOADED with the epoch the chunk now holds. The commands held for a loading chunk ignore the block quota (they spend it all the same). | The brief's order. It also matters to the engine: on IND_CHUNK_LOADED it counts every pending epoch at or below the reported one as "applied as asked" (engine.rs, review finding 13), so a result that arrived after the LOADED record would have been read as a duplicate of a full application, shortfall lost. Nothing of the chunk has ticked yet, so deferring part of it to a later tick (the quota) would reopen the stale-tick race. |
| R2 | **The hook: `ChunkEvent.Load` gates ticking; the reconcile lands at the next drain.** At `ChunkEvent.Load` of a chunk with a held command, the chunk and the district's other loaded chunks stop ticking block entities: a mixin on `LevelChunk.isTicking(BlockPos)` (PATCHES.md row 25) answers false while the chunk's gate is set. Loads drain at `ServerTickEvent.Pre`, before any level ticks, and at the end of the tick as before; the drain applies the held commands (R1) and lifts every gate. A gate lapses by itself after 20 server ticks. | Ordering in 1.21.1: `tickServer` posts `ServerTickEvent.Pre`, then each level ticks (block ticks, chunk source, entities, `tickBlockEntities`, entity manager), then the GameTest ticker, autosave and `ServerTickEvent.Post`. Every block entity ticks through `LevelChunk.BoundTickingBlockEntity.tick`, which asks `LevelChunk.isTicking` first. `ChunkEvent.Load` itself is posted from `ChunkStatusTasks.full` on the server thread, inside the chunk system's main-thread task: mostly between ticks (`waitUntilNextTick` polls the chunk tasks), sometimes inside a tick (any synchronous `getChunk` runs pending tasks). Load is early enough, but applying there is not safe: a destroy's neighbour updates and a plugin's multiblock code can load another chunk synchronously from inside the chunk task. So the event only gates, and the apply waits at most until the next drain: for a load between ticks that is `Pre`, before anything ticks at all; for a load inside a tick, the end of it, with the district's machines held still meanwhile. The gate is one `int` read per `isTicking` call when unset. |
| R2a | Rejected hooks: applying inside `ChunkEvent.Load` (above); a mixin on `ChunkStatusTasks.full` or `LevelChunk.runPostLoad` (the same task context); keeping the chunk below BLOCK_TICKING through its ticket level (a player's ticket cannot be lowered); gating the chunk alone (a funnel or hopper in the next chunk of the district could pull from it in the same tick). | |
| R3 | **What the gate does not hold.** Entities (item entities, hopper minecarts) and scheduled block ticks of a gated chunk are not held: both need the chunk's entities loaded, which a chunk rarely has in the tick it loads (the entity manager finishes loads at the end of the level tick). A machine outside the district, and a synchronous neighbour load (a hopper in a ticking chunk reading a block entity of the next, unloaded chunk) act before the drain. A player who arrives without an approach (logs in inside the district, teleports, comes through a portal) gets the engine's commands after IND_CHUNK_LOADED, as before; their shortfall is trimmed (I8). | The residue is small and was there before; the shortfall path keeps the books right. |
| R4 | **The engine sends a held reconcile again after a restart.** Java holds commands in memory only. `Engine::sent_this_session` (op ids sent since the session start, not saved) lets each closing IND_APPROACH send again every pending command not sent in this session, also while a hold is active; within a session a command goes once. Test: `after_a_restart_the_next_approach_sends_the_held_reconciles_again` (rework.rs). | Before, `sent` was saved with the command, so after a restart the commands Java had held went only at IND_CHUNK_LOADED, after the chunk ticked: the stale-tick race came back for exactly the districts that had been reconciled ahead. Clearing the saved `sent` flag at a session start was rejected: trims rewrite unsent commands in place, and a command applied and saved with its chunk but whose result was lost would then be trimmed after the fact. |
| R5 | **IND_APPROACH for partly loaded districts, closing per player.** Every 20 ticks, for each district with a chunk that is not loaded (whatever its load state): each player within `approachRadiusBlocks` of the nearest such chunk is compared with that player's own distance 20 ticks before. Closing: some player's distance fell. The record carries the closing player who arrives first (distance, ETA = distance / rate), else the nearest player's distance and an unknown ETA. Once every chunk is loaded, no records. The distance is to the nearest unloaded chunk, not the district's box. | The brief: "Send IND_APPROACH for partly loaded districts too, with closing accurate". One district-wide "last distance" made a second player standing still read as closing whenever the nearest player changed; per player it cannot. The box distance of a partly loaded district is 0 for a player inside it, though the unloaded part may be far. |
| R6 | **Test hooks.** `Reconciler.restartForTest(long... rolledBack)` drops the held commands and the "journaled again" marks (what a restart loses) and forgets the given op ids in the journal's applied set (`Journal.forgetAppliedForTest`: the journal rolled back to the last save). | The crash test needs the exact losses of each crash point, on the real server. |
| R7 | **Far-chunk GameTests get long timeouts** (12,000 to 16,000 ticks), `aHeldReconcileAppliesWhenItsChunkLoads` too, and the new ones wait 5 ms per tick while a wait's check fails (`io(...)`). | The GameTest server ticks unthrottled, so generating, loading and unloading a far chunk costs thousands of ticks; at 2,400 that test failed by timeout on a loaded machine. Ticks alone were not enough: with the laptop busy, a far chunk's entities (which a block entity needs loaded to tick) took longer than 12,000 unthrottled ticks, about 5 s, and the hopper and belt tests failed. A sleep only while waiting bounds the wait by wall time and costs a passing run nothing it was not already waiting for. |
| R8 | **The hopper test holds its chunk at FULL** with a region ticket of level 33 (generated first under a forced ticket), so the hopper never ticks while the test builds it. | A forced chunk ticks: the hopper would pull before the unload. |

## Part 2: repair schematics (I1)

Ben's I1 answer: repair schematics now; damage scaling with progression, a wrench fix and the rewind
device are deferred. Built here: the schematic.

| Id | Choice | Why |
|---|---|---|
| R10 | **What counts as destroyed.** Before a reconcile breaks a block, the core records the states of the block, its six neighbours and whatever a plugin says goes with it (`IndustryPlugin.alsoBroken`; the Create plugin adds a belt's segments), in loaded chunks only. After the command's breaks, every recorded position whose block changed is what the sim destroyed (`IndustryPlugin.destroyed`, with `DestroyedBlock(pos, state before, rebuild data)`). A changed state of the same block (a fence losing a connection) is not destroyed. Player breaks never pass here. | Breaking one Create belt segment removes the whole belt and leaves shafts at its pulleys (`BeltBlock.onRemove`); a torch or a door half goes with its support. Only positions known before the break can be rebuilt. Cascades after the call (a scheduled tick, falling sand) are not caught. |
| R11 | **Mod-agnostic in the core, Create in the plugin.** The core snapshots and reports; `RepairSchematics` (create plugin) writes the file and the item. | D4: the core knows no mod. Another plugin could rebuild some other way. |
| R12 | **The file**: `schematics/uploaded/mic-rtsim/repair_d<district>_<gameTime>.nbt` under Create's `CreatePaths.UPLOADED_SCHEMATICS_DIR` (the game directory, not the world). | The cannon loads `<uploaded>/<owner>/<file>` and never checks that the owner is a player. `mic-rtsim` cannot be a player name (a hyphen), so no player's upload trims the folder (Create deletes only the uploader's own oldest file past `maxSchematics`). Create's upload size limits apply to uploads only; the cannon reads any size. |
| R13 | **The contents**: a sparse structure template (`StructureTemplate.save`'s layout, gzipped, the current DataVersion) of only the destroyed positions, each with its state before. Block-entity data: what the cannon would place itself (`BlockHelper.prepareBlockEntityData`: full data only for Create's `safe_nbt` blocks, the safe behaviours of smart block entities, signs and banners), plus, for a belt, `Length`, `Index`, `IsController`, `Controller`, `Casing`, `Covered` and `Dye`, which the cannon reads to lay the belt again. No inventory is ever written. | The brief: "leave out block entity data except what Schematicannon places safely". Cells left out of a template are not printed in the default mode. Without its length a belt prints as nothing. |
| R14 | **One schematic per district per wave of damage**: what one district loses within 100 ticks of its last loss is one schematic, written and delivered once 100 ticks pass with none. | Several attacks while a player is away all land at the load, chunk by chunk over a few seconds: one schematic to print, not one per attack and chunk. Damage after a visit is a new schematic, so an item already handed out never changes under its anchor (a file rewritten with a wider box would move its corner). |
| R15 | **Delivery: on the ground at the damage.** The item is dropped at the destroyed block nearest the middle of the damage, among the drops, and never despawns (`ItemEntity.setUnlimitedLifetime`). If no destroyed block is in a loaded chunk at that moment, it waits until one is. | Found in the world where the player looks first, with no new block or item (D3) and nothing shown (I18 rules out a chat line). Rejected: a container of the district (automation can carry it off, and which one?); the owner's inventory at the next login (Java has no district owner: the only owner is the engine's P14 owner by time spent, an `ActorId`; see "For Ben"); the district's postbox as a package (only districts with Create logistics have one). A hopper under the damage can still pull the item in; it stays in the factory. |
| R16 | **The item**: Create's own `create:schematic` (`SchematicItem.create(level, file, "mic-rtsim")`), with `schematic_deployed` true, `schematic_anchor` the template's corner, rotation and mirror none: it goes straight into a Schematicannon and prints in place. No custom name. | D3; Create's own GameTest makes its schematic the same way. A name would be district output (I18). |
| R17 | **Cannon settings untouched; a belt needs "Replace Block Entities".** The player picks the cannon's options. The default ("replace any", block entities kept) prints every destroyed block except a belt: Create prints a belt from its last pulley (`stripBeltIfNotLast`, then `BeltConnectorItem.createBelts` over the whole length), and the break left that pulley a shaft, a block entity, which a cannon replaces only with "Replace Block Entities" on. The GameTest turns it on. Create lays the belt from that pulley back, so it comes back facing the other way (START and END swapped); it carries items the same way, since a belt's movement follows its axis and the shaft's rotation only (`BeltBlockEntity.getMovementFacing`). | A sparse template already limits the print to the holes, so replacing block entities there touches only what landed in a hole since. Making the default print belts takes a mixin on Create's cannon (see "For Ben"). |
| R18 | **No preview on clients (UNVERIFIED in game).** Create's client renders a deployed schematic from its own local `schematics/` folder, which never has the server's file. The cannon prints it all the same. | A Create limit; uploading to clients is out of scope. |
| R19 | **Pending damage lives in memory.** A crash within 100 ticks of the damage loses that schematic (the drops are in the world). A schematic delivered twice prints nothing the first did not. | Nothing is minted or lost by a missing or duplicate schematic, so it needs no journal. |
| R20 | **The GameTest**: an offline raid through the reconcile path an unwatched attack's damage takes (destroy entries, held while the chunk is unloaded, applied at its load): a three-segment belt, an andesite casing with a torch, a chest; a casing a player broke next door. It checks the file holds exactly the destroyed blocks with their states before, no inventory and the belt's length, the item lies at the damage, deployed and anchored, and a real Schematicannon with a creative crate prints every block back (Create's own `TestMisc.schematicannon` pattern). | The engine's threat resolution has no Java caller (`INDUSTRY_THREAT`, order 8, is unused): the test scripts the reconcile the resolution produces, on either engine. |

## For Ben

1. **The journal can be ahead of a chunk (found while writing the crash test; not changed).** Autosave
   writes the journal (`JournalSavedData`, synchronously) before the chunks' IO worker writes them. A
   crash between leaves a chunk older than the journal: the engine gets the reconcile's result from the
   journal, the chunk on disk never had it, and nothing sends the command again (the chunk's
   IND_CHUNK_LOADED reports the older epoch, but the command is no longer pending). Goods are lost, never
   minted. A fix: the engine keeps a chunk's last applied command until an IND_CHUNK_LOADED reports that
   epoch, and sends it again when a load reports less; Java then dedups reconciles by the chunk's epoch
   only. Recommended, as its own change.
2. **Repair schematic files are never deleted.** A few kB each. Options: keep all (now); delete a district's
   files older than N days; delete when the district is forgotten.
3. **Delivery to a player.** If you would rather the schematic went to the district's owner (at the next
   login, or into their inventory now), the Java side needs an owner: the engine's P14 owner by time spent
   would have to come over the boundary. Recommended: keep the drop at the damage (R15).
4. **Belts print only with "Replace Block Entities" on (R17).** A player who loads a repair schematic with the
   cannon's defaults gets everything back but the belts, and the cannon reports itself finished. Options:
   leave it (Create's own rule, the same for any schematic of a broken belt); a small mixin on
   `SchematicannonBlockEntity.shouldPlace` letting a cannon lay a belt pulley over a shaft of the same axis
   (all schematics, not only repairs). Recommended: the mixin, if belts break often in raids.
